# 补员归队诊断：测试步骤

这是独立诊断插件，可与现有星政中枢同时启用。默认关闭，只写日志和诊断标识，
不修改舰队命令、舰船组成或补员队列。它与“同星系散舰归队试验版”相互独立。

构建命令：`python tools/build_reinforcement_probe.py`。
生成目录为 `dist/fleet_reinforcement_probe`，旁边的 `fleet_reinforcement_probe.mod`
是启动器描述文件。当前电脑已复制描述文件到群星 Documents/mod 目录；未改变启用列表。
源目录移动后需重新构建并更新启动器描述文件中的路径。

## 玩家操作

1. 启动器当前播放集中添加并启用 **补员归队诊断（仅记录）**，保留原有中枢。
2. 使用非铁人测试档或另存的副本，在法令中找到同名入口，点击 **开启或续期诊断**。
   也可用控制台 `event qol_reinforcement_probe.1` 打开菜单。
3. 给两支主舰队起不同的名字，例如“测试A”和“测试B”，让它们同时补充同一种舰船。
   在管理器增加几艘同型号舰船的目标数量也可产生补员需求。
4. 新舰船已经建好、仍在补员途中时，手动另存 **补员途中.sav**。
5. 让测试A进入战斗，观察是否产生独立小舰队；出现后另存 **补员散舰后.sav**。
   此时先不要手动拆分、合并或给散舰改命令，便于保留故障现场。
6. 如果局面允许，继续运行约60个游戏日，覆盖后续记录。回到诊断菜单点击 **停止诊断**。
7. 回聊天告知“测好了”。日志和存档仍在本机，助手可以直接读取，无需手动翻日志。

不能复现时也可告知实际经过；没有复现不等于证明机制正常或无法修复。
游戏下次启动可能覆盖 game.log，测试结束后优先回到聊天。

## 记录内容与结论边界

`Documents/Paradox Interactive/Stellaris/logs/game.log` 内搜索 `QOL_PROBE`。

- 开启时记录舰队名单，为同名舰队生成不同的诊断编号。
- `on_ship_built` 记录新舰船编号、名字及实际存在的 FROM 名称。
- 记录新舰船当时所在舰队、星系、是否交战、是否存在原版合并命令。
- 完工后第1、5、20、60天分别采样，比较当前舰队和出生时舰队。
- 停止诊断后，已排程采样也会跳过；180天后开关自动过期。
- 舰船若被摧毁，其后续事件可能不再发生，不能把没有日志解释为成功归队。

**出生时舰队不是原补员目标。** 本插件不会把这两个概念混用。
游戏导出的接口中尚未找到原补员目标的读取方式；本轮采样主要验证回调时机、
当前舰队和命令状态是否可观测，再对比两份存档中的补员数据。
存档里存在目标信息也不代表 Mod 脚本能读取它。
只有后续定向验证能稳定区分测试A和测试B的真实补员归属，才可承诺自动保护。

目前通过构建、括号、本地化和事件引用的静态检查；未通过游戏内执行验收。

## 第二轮与定向读取测试（0.1.2）

第二轮已确认普通造船回调、当前舰队、合并命令检测和延后采样可执行；
本轮未出现诊断插件相关错误。最新测试存档为2201.03.26，其中仍有三支补员舰队保存原目标。
日志和存档备份在开发目录 `scratch/probe_20261016_round2/`。

完整 scopes 文档未列出 `original_merge_fleet_target`。
因此新增**仅手动执行**的事件，测试把这个真实存档字段名用作脚本目标是否受支持。
该用法是待验证的候选，不是已确认的接口，也不会用于正常采样或舰队命令。

更新测试文件后，完全退出游戏并重新启动（仅返回主菜单不够）。
加载2201.03.26测试存档并保持暂停，在控制台输入：

```text
event qol_reinforcement_probe.100
```

不必开启诊断、不必新造船、不必推进时间；事件只统计带合并命令的自有舰队并写日志。
当前实机已确认 `reload events` 返回 Failed to reload，不能用它加载本次新增事件。

判断标准：

- `sources=0`：没有检查到候选舰队，本次无结论，需要核对加载的存档。
- `sources>0` 且 `owner_controls=sources`：正对照成立，说明舰队作用域有效。
- 正对照成立但 `candidate_readable=0`，且引擎报未知目标/作用域：此字段名不能当脚本目标读取。
- `candidate_readable>0`：仅说明存在性检查通过，还要验证解析出的目标与存档真实ID一致，不能立即承诺自动归队。

负结果只否定这项具体读取方式；结合完整导出接口清单，当前仍不能承诺原版纯脚本的全自动归属恢复。

## 定向测试实机结果

2026-10-16 22:57，在2201.03.26测试存档暂停时执行`.100`：

```text
QOL_TARGET_TEST RESULT sources=3 owner_controls=3 candidate_readable=0
```

三支来源舰队均被遍历，owner正对照均通过。引擎明确报告第119行
`exists` 正在检查未定义作用域（`is checking against an undefined scope`）。
同一存档此前已确认三支来源都有 `original_merge_fleet_target=16777494`。
因此排除了“存档里本来没有目标”与“没选到补员舰队”这两种解释，
证实该存档字段名不是可直接使用的脚本作用域。

这不等于证明所有外部扩展或未发现的途径均不可能，但结合完整导出的scope清单，
目前没有能支撑“提前开启后全自动恢复原补员归属”的公开脚本接口。
不要把现有同星系收编试验版描述为此问题的修复，不再要求玩家重复普通补员采样。
