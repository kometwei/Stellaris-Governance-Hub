# 批量散舰整理工具 0.2.4

当前阶段：只做整队批量合并，不做指定配置或拆船。
独立插件，可与星政中枢并用，不依赖补员诊断或已停用的倒计时试验。

## 0.2.4：修复0.2.3实测发现的作用域错误

本次游戏日志在混编分组和`qol_fleet_sort.20`下令事件中均出现
`Wrong scope for trigger 'any_owned_ship'`，当前作用域是ship，要求country／fleet。
原因是将`prev.prev`／`prev.prev.prev`错误当成历史回退；原生对应写法应为
`prevprev`／`prevprevprev`，本机游戏导出的`scopes.log`有明确说明。
该错误也阻断了单一设计舰队的最终下令，不能视为只有混编失效。

0.2.4已替换上述写法；构建器禁止再次生成`prev.prev`。离线模型使用原生历史作用域名，
拒绝舰船作用域中的`any_owned_ship`，并检查确认后清理计划再派发的路径。
新增`QOL_SORT DISPATCH_REJECT`日志；PREVIEW／COMMIT日志包含版本号以确认实际载入版本。

本次旧日志有`issued=5`，没有`QOL_SORT ORDER`，且伴随派发事件作用域错误，
表明未进入原生命令分支。即使后续出现ORDER，仍只能证明进入下令分支，不能证明归队成功。
**0.2.4离线45项通过，原生报错是否消失及实际归队仍待完全重启游戏后复测。**

## 使用

1. 启动器启用“散舰整理工具（试验）”，完全重启游戏。菜单与预览标题显示0.2.4。
2. 仅在保护名单设置想保留的例外。不需要逐页挑选待整理舰队。
   已经“保护全部”过的，可一键取消全部手动保护，再保护少数例外。
3. 点击“扫描并预览本批散舰”，核对参与数量、设计集合组数、预计编队、请求数和参与的混编数量。
4. 有请求时点击确认；零请求时不提供执行按钮。也可以取消，预览不会改变舰队命令。
5. 每批最多256支候选。几百支可通过“预览下一批”继续，无需逐舰选择，也不会后台自动循环。
6. 本工具此前的接收队如果仍在等舰船，只能继续接收并保留容量。
   确认本工具安排的全部归队已完成或取消后，再点击“释放旧容量预留”，允许重新整合旧接收队。
   接收队停下不代表所有在途舰船已抵达。失败或取消的请求也要手动释放预留。

控制台入口：`event qol_fleet_sort.1`。此版不能靠`reload events`可靠加载，需完全重启。

## 手动批量制造测试散舰

在测试存档中，控制台输入：

```text
event qol_fleet_sort.50
```

选择20、100、300或600支，每队生成一艘，全部采用从现有自有常规军事舰队中
抽取的一份实际设计，出生在首都恒星旁。需要至少一支可作为样本的常规军事舰队和首都，
否则数量按钮不显示。只给新生成的测试舰队设置出生位置，既有舰队不移动或拆分。

先用20支检查生成是否正常，再用300支跨256批次上限测试。可以在生成前用工具
“保护当前全部舰队”保留现有编队；新生成的舰队不带保护。返回普通整理菜单扫描并确认，
推进时间观察归队。生成会增加军力和维护费；测试结束读生成前的存档恢复。

此入口只接受控制台手动调用，没有接到法令、普通菜单或后台事件。测试生成事件在
`events/qol_fleet_sort_test.txt`，普通整理脚本仍禁止创建、删除、复制或传送舰船。
创建后重新遍历本批带批次标记的舰队，结果显示实际读到的一船舰队数；并非合并成功数。
生成入口本身仍待实机触发验证，离线模型不等同原生效果。

### 0.2.3混编对照组：本次建议优先测试

1. 在测试存档中准备至少两种不同的实际军舰设计，保存后在工具首页“保护当前全部舰队”。
2. 输入`event qol_fleet_sort.50`，选择“生成8支混编／单设计对照舰队”。
   若按钮不出现，检查现有常规军事舰队中是否确实有两种设计及首都。
3. 生成AB、BA、AAB三支未保护混编队、一支受保护AB、两支单设计A、两支单设计B。
   A和B来自现有舰船的两种实际设计，现有舰队不拆分、不移动。
4. 返回首页预览。若其他舰队均已保护，且指挥上限足以容纳4艘A与3艘B的指挥点数，
   应为7支参与、3支参与混编、3个设计集合组、3支预计保留编队、4条请求。
   若总指挥点数超限，会整队另开编队，请按实际容量判断，不强求4条请求。
5. 先查看分组，排除混编样本组，应只排除AB／BA／AAB；单设计A、B仍可各自合并。
   使用“清除本次排除”恢复，再确认执行。受保护AB应始终保持不动。
6. 推进时间，核对AB／BA／AAB实际汇入同组目标、单设计A和B分别归队，
   全部8支测试舰队中的舰船总数仍为13艘，受保护AB仍保有2艘。
   容量足够时，三个未保护集合组应分别为7艘混编、2艘A、2艘B。
7. 再做跨星系、连续批次和预览后升级设计的测试。混编预览后改变舰船数量、身份或设计，
   本批会保守跳过受影响的请求，重新预览后再确认。

界面、生成器和原生归队均待游戏实测。ORDER／issued只代表下令尝试，
必须以实际归队、舰船数及设计保持来验收。测试完读生成前存档恢复。

## 本阶段规则

- 所有符合条件的未手动保护军事舰队，不限一至三艘、不要求旧接收队身份，也不要求逐队授权。
- 按完全相同的实际设计对象集合分组；相同设计名但不同实际设计版本不会归一组。
  AB、BA、AAB属于同一组；A、AB、ABC、AC属于不同组，不做子集／超集兼容匹配。
  每种设计的数量比例和舰船顺序不影响集合相同判断。
- 单一设计与混编都只做整队合并，舰船身份保持不动。普通整理没有拆分、复制、删除或传送舰船的效果。
- 按整支舰队和实际指挥点数装入目标，放不下另开一队。按遍历顺序next-fit规划，
  不拆船，不保证最优装箱或每队恰好满编。
- 手动保护的舰队在预览、确认和执行中均跳过。一键取消保护只清手动保护，不清容量记录。
- 保留原有可用性限制：自有且本国控制、可移动常规军事舰队、有可用星系、无领袖、
  不交战、不租借、不属于联邦舰队。正常补员合并、维修升级及其他特殊任务仍跳过；
  普通移动、跟随、返回允许，确认后来源旧移动命令被替换，目标保留原有移动。
- 每支舰队不得已经超过国家指挥上限。混编统计为本批实际参与的混编数量，不再表示跳过数。
- 新接收请求的目标保留接收身份和容量预留，防止连续批次重复利用在途容量。
  容量基数是`max(实际规模, 已预留总规模)`，抵达舰船不会重复计算。
- 混编来源和目标在预览时记录舰船数量和逐船实际设计；确认时组成变化则保守跳过。
  即使来源与目标同时变为另一相同集合，也不能沿用旧预览。仅调换舰船顺序不影响检查。
  在预览后有同设计舰船抵达目标，也需重新预览；已经预留的容量仍保留。
- 分组排除按本批分组索引处理，不按样本中的某一个设计排除。按钮显示样本舰队名及其中一种设计，
  混编的完整组成请结合样本舰队核对；共享某种设计的其他集合组不会被连带排除。

保护名单和设计详情的分页均为可选查看操作，批量规划和执行不依赖分页选择。
0.2.2起两种列表每页8项，提供首页/末页/上一页/下一页，边界处隐藏无效按钮。
保护名单支持只看已手动保护、查看全部；切换筛选回第一页，返回重进保留页码。
受保护视图解除一支后重建列表并收紧页码，避免尾页变空；刷新也保留仍有效的当前页。
旧版每页4项留下的偏移会归整到8项页边界。设计预览重算会重建分组并回首页。
实际事件窗口显示密度与滚动布局仍待实机检查。
目前没有按名称输入搜索的界面，不将先前讨论的搜索想法当作已实现功能。

## 开销与验证

没有on_actions、日/月脉冲、延迟事件、后台重试。只有玩家打开菜单或点击操作才运行。
单一设计快路径保留三轮舰队扫描。混编额外在本批代表舰队中查找相同集合，
每支进入批次的混编会额外遍历拥有的舰队以筛出代表，再双向检查设计成员。
代表数受每批256支限制；单次集合比较最坏与双方舰船数量乘积成正比。
来源舰队不再限三艘，开销包含这些舰队的全部舰船；保护和任务等廉价筛选前置。
混编扫描开销高于单一设计路径，大批混编存档的响应速度仍需实测。

45项离线回归通过：

- 第1、第4普通五艘同设计舰队无需名单授权即可规划合并，占用400/1100。
- 500支单一设计混合规模舰队加一支混编直接批量处理，256支进入本批、245支留待后续。
- 同设计大舰队参与、手动保护保留、混编按设计集合参与，预览不下命令。
- 命令容量预留、上限降低、状态和设计变化、旧接收队重组、稳定分页等。
- 手动测试生成四种数量的一船舰队、设计/所有权/位置传递和原舰队保持；缺少样本不生成。
- 首页末页的空列表/整页/余页边界、保护筛选重排与页码记忆、设计分组跳页、旧版偏移兼容。
- 混编同集合不同数量和顺序、子集/超集/交集/版本隔离、整队容量边界、在途预留和旧接收队重组。
- 混编来源/目标或两者同时变化的复查、上限降低、300支混编的256批次边界、共享设计的分组排除。
- 原生派发事件分支的模型检查（仍不执行游戏原生动作）；8支混编对照组的采样、生成和计划结果。
- 原生prevprev／prevprevprev历史作用域、错误舰船遍历拦截、清理计划后单设计与混编映射进入派发分支。

模型执行生成的规划脚本，不是游戏引擎，不验证原生动作、动态目标保存、事件上下文或寻路。
日志的ORDER和issued都是尝试，不等于合并成功。现有日志已出现第8→第11的请求，
尚未据此确认实际完成合并。当前还需用新版本测试存档验证同星系与跨星系实际归队。
