# 恒星基地清空（待实机验收）

## 0.2.5：建筑改为按实际槽位移除

用户截图为 0.2.4 失败结果。日志这次明确证明 mode=2、reason=0、REMOVE_BEGIN category=buildings 均出现，且建筑从 4 降至 3；因此是部分移除，不能说建筑分支没执行。逐类型随机移除路径未达到完整清空目标，停止继续依赖该路径。

建筑改用原版 `01_start_of_game_effects.txt` 使用的 `remove_starbase_building = { slot = 1 }` 形式。按已审计的不分类槽位数量，从高到低对实际范围内的槽位发出字面量参数，不固定四格，也不传入未证实支持的变量 slot 参数。生成上限仍受 1024 保护界限约束；空槽无设施可删，槽位本身、等级和容量不被设置。模块继续使用已实测有效的原逻辑。

新增空洞布局、12 个槽位样本的模型检查。建筑执行记录 REMOVE_SLOT；审计继续打印 mode、安装数量及槽位计数。模块逐类型日志改由国家作用域复制计数后打印，修正此前在基地作用域打印变量为空的问题。标题显示 0.2.5。新建筑槽位路径尚待游戏内验收，不将模型检查作为原生成功证明。

## 0.2.4：建筑独立移除路径与逐项诊断

0.2.3 实测建筑仍未移除。审计日志显示 reason=0，建筑数保持 4，没有相关作用域错误；尚无足够记录区分模式选择、分支是否进入及原生调用是否拒绝，不能声称已确定建筑接口无效。

建筑改用本机 effects.log 和模块示例文档明确列出的 `remove_random_starbase_building = { type = <已核对的建筑> count = 1 }`。每次只匹配指定类型，次数按该类型已安装数量限制，不使用随机无类型删除；所有前置保护不变。模块继续使用用户已实测有效的 `remove_starbase_module`，不增加取消造舰、移除舰船或重建基地操作。

审计日志新增 mode（1 模块／2 建筑／3 全部），每个类别记录 REMOVE_BEGIN；实际匹配到的每类设施记录 REMOVE_TYPE、before、after。标题显示 0.2.4。下一轮先单独选择“清空全部建筑”，核对确认页建筑数量和保留模块说明；若仍不生效，应按分支与逐项日志定位，不再仅根据离线模型推定引擎行为。此建筑接口路径尚待实机验收。

## 0.2.3：空槽不再阻止下一次清空

用户实测模块可以拆，建筑未能清空；生产舰船期间船坞未被拆除。日志显示原生模块移除后，不指定类型的计数仍为 6，而逐类型汇总已为 0（另一例仍有 1 个模块），随后 reason=5。旧版将两者差值认作未知设施，导致模块拆完后无法继续操作建筑，也无法正确确认清空成功。

已改为按类型汇总已安装数量及包含设施施工的数量；不指定类型的原生计数只用于诊断／边界检查，不据此把空槽判为未知。新增先清模块再清建筑、模块为空时单独清建筑的回归场景，并模拟用户日志中的 6／4 空槽仍保留计数。模块原生移除写法保持不变；原生拒绝移除船坞时不重建、降级或取消订单来绕过。用户对造舰时船坞受保护的观察仅记录为本轮实测，不泛化为所有生产场景都可靠。

未知设施检查相应改为明确检查构建时播放集中的 Mod 新标识、同名覆盖标识和相关在建项目。公开版仅原版目录，无法对构建后任意新加入的 Mod 标识进行通用未知检测；启用或更改设施 Mod 后必须重新生成对应本地版。这是当前接口边界，不能再声称运行时无条件识别全部未知设施。

## 0.2.2：改用明确设施类型移除

用户复测仍无法清空；game.log 证明已进入 execute 并完成前后两次 audit，未见移除作用域报错，不能再把问题归因于入口未加载。旧版使用空参数 remover，文档虽说明参数可省略，但此组合没有通过实机验收。现改为原版 `common/scripted_effects/espionage_event_effects.txt` 已使用的 `remove_starbase_module = { module = anchorage }` 等显式类型写法，建筑同理。每种设施先计数，再进行有界移除；每次调用前检查仍存在该类型，以兼容原生一次移除一个或全部同类设施的行为。未知设施及其他保护检查保持不变。

日志还报告 `Invalid macro entry`，原因是 scripted effect 内动态日志没有按原版 `99_advanced_documentation.txt` 要求使用双反斜杠转义。已修复，保留明确版本和审计数值。新模型不再假设空参数即可清空，新增“原生每次删一份／删所有同类”两个场景。标题显示 0.2.2；真正的原生移除效果仍需复测，不把离线模型视作实机成功证明。

## 0.2.1：修正设施目录中的内联模板

用户截图显示“强拆已开启”，但界面因未知设施检查未通过而不提供清空操作。实机 error.log 报告 `Failed to find starbase buildable inline_script in database`；旧扫描器误将原版目录顶层的 `inline_script` 调用作为设施标识，也漏掉了其生成的 voidlure 系列。已按参数展开原版顶层内联模板，并检查循环、路径和未解析标识。新增测试确保生成脚本没有 `type = inline_script`，且包含实际生成的设施标识。

标题显示 0.2.1，未知设施页增加总数／识别数，game.log 增加 `AQSC AUDIT version=0.2.1` 及总数、识别数、含施工数、拦截原因。此修复消除了已确认的目录错误；是否完整解决本次拦截仍需修复后实机复测，不将原有静态模型当作证明。强拆仍不绕过真正未知的设施。

入口：“打开星政中枢 → 恒星基地清空”。选择基地，查看状态和现有数量，选择“清空全部模块”“清空全部建筑”或“两者全部清空”，确认后立即移除。控制台入口：`event auto_qol_starbase_clear.1`。

每批列出十座自有普通升级基地，同一轮浏览不重复。下一批浏览完毕后可从头浏览。“下一批／从头浏览／空列表”互斥，按同时可见的最大行数计算，十座基地加一个批次操作共十一行；返回首页与关闭保留同页底栏，不产生额外布局分页。受保护基地可选择查看跳过原因，不提供可执行的清空按钮。目标在选择后被摧毁、被占领或转移所有权，也不会被执行。

### 强拆开关

基地详情页提供默认关闭的强拆开关。开启后仅放宽防御平台容量来源设施及船坞／兽坞的保护；三个清空范围都仍需单独确认。确认页显示容量超限及可能影响造舰订单的提示。不主动拆除平台、离子炮、舰船或取消订单，但原生移除与后续引擎处理可能影响生产或容量，尚待实机验证。

更换所选基地、重新进入本功能或从头浏览会关闭强拆。刷新当前基地、进入确认及取消返回保留当前开关；执行前再次读取开关。全国限量、特殊移除条件、额外模块／建筑槽位、未知设施、已检测到的施工、升级、占领或战斗检查均不能被强拆绕过。

## 操作范围

- 模块使用 `remove_starbase_module = { module = anchorage }`，建筑使用 `remove_starbase_building = { slot = <字面量槽位> }`；建筑只发出已审计槽位范围内的操作，按实际范围有界执行。
- 只操作选中的一座基地；所有移除都在确认选项的隐藏效果中执行。选择、查看、刷新和取消均不移除设施。
- 不写基地等级、槽位数量、修正、资源或舰队命令，不复制、重建或降级基地。原版有额外槽位的基地不依赖固定六模块／四建筑假设。
- 即时生效、不退款，不是排队拆除。移除设施后失去其正常修正属于预期效果；清空模式之外的设施不主动移除。
- 不加入月度或每日事件，不覆盖原版恒星基地界面。原生事件选项负责进入、返回、确认与关闭，避免效果按钮另外叠窗。

## 保护规则

保护整座基地，与本次选择清模块还是建筑无关：

1. 基地不是自有且由自己控制的四种普通升级基地，或正处于交战状态。
2. 基地舰队 `is_upgrading = yes`；或者按已识别设施类型汇总的 `include_being_constructed = yes` 数量与已完成数量不同。构建时播放集未适配的 Mod 在建设施按明确标识阻止；达到计数上限也跳过。
3. 含显式 `empire_limit` 的模块或建筑。动态全国限量同样保护，不因为当前限量尚未用满就允许拆除。原版征募办公室因此保护整座基地。
4. 含自定义 replaceable、destroy_trigger、隐藏特殊 potential 或直接提供 `starbase_module_capacity_add`／`starbase_building_capacity_add` 的设施，保守保留，避免槽位或特殊逻辑受到影响。含 `starbase_defense_platform_capacity_add`／`starbase_defense_platform_capacity_mult` 的设施默认同样保护整座基地；只有不具备上述其他保护原因时，强拆才能放宽这项容量保护。
5. 含船坞或兽坞默认跳过。强拆可放宽这项保护，但不表示其生产队列已通过检查。当前没有经过验证的造舰／防御平台队列读取接口；设施队列和基地升级之外，防御平台队列仍没有完整检测证据。首轮测试请使用没有其他生产队列的基地。
6. 含构建时播放集中新增或同名改写、未被原版识别目录收录的设施，或这些设施正在建设。使用明确设施触发器检查；不指定类型的计数在实机中会保留空槽，不能用它减去已识别数来检测未知设施。计数使用有界 while，不依赖未验证的 count trigger 导出行为。

查看详情、进入确认及真正执行前都会重新检查。执行后重新计数，只有选定类别归零且仍通过保护检查才显示成功。模型覆盖原生移除失败时不误报成功；原生接口或回调产生的部分变化不能自动回滚，需实机验收。

## Mod 范围

公开版的识别目录来自本机原版定义。公开版无法运行时检测构建后任意新增的 Mod 设施标识或原版同名设施改写；涉及设施 Mod 时需生成对应本地版。

播放集更改后请重新生成本地版。已接入本地发布构建：扫描播放集目录 Mod 的设施定义，将同名覆盖从识别目录排除；descriptor.mod 的相关 replace_path 会保守排除对应类别。没有实现通用归档 Mod 覆盖解析，也不能保证发现未登记文件覆盖或脚本间接改变槽位的规则。此版不承诺清空这些未知组合。Mod 自己新增的更高基地等级、星环、方舟等均不进入列表。

`starbase-clear-build.json` 记录已识别、受保护、因 Mod 覆盖排除的标识及计数上限。保护目录按构建时读取的定义生成；更新游戏定义后应重新构建。

## 验证与游戏内测试

```text
python tools/build_starbase_clear.py
python tools/build_hub_gui.py
python tools/test_starbase_clear.py
python tools/test_hub_gui.py
python tools/test_native_dashboard_footer.py
python tools/build_release_profiles.py public
```

公开版与本地版构建均生成本功能。新增 GUI、scripted effects 和 triggers 后完整退出并重启游戏。

自动测试执行实际生成脚本的作用域模型，覆盖三种模式、其他基地不受影响、原有等级和额外槽位保留、未知设施、全国唯一、队列、升级、失效目标、占领、战斗、AI、确认后状态变化、分页、构建覆盖和原生失败检测。它不等价于游戏内测试。

建议在存档副本中：

1. 选择没有船坞／兽坞、没有施工、没有唯一建筑的普通基地，例如若干锚地或贸易模块加资源仓库。分别测试三种清空操作，确认每次只影响所选基地和所选类别。
2. 检查详情、预览确认、取消、首页返回和关闭；仅浏览或取消不得移除设施。确认清空后检查原有等级、可用总槽位和资源均保持预期。
3. 在独立样本放征募办公室、未知 Mod 设施、正在施工的模块／建筑、排在其他订单之后的设施订单，分别确认显示跳过且设施仍在。另检查基地升级、含船坞和已被占领的样本。
4. 从确认页面切回游戏改变状态，再确认操作，验证后端重新检查。再次点击已清空类别不应产生额外改变；保存读档后复查。
5. 有额外槽位的基地需单独确认原生 remover 不改变槽位容量。检查 error.log 中的作用域、count、while 和 event target 报错；队列计数含义、remover 行为、回调及复杂 Mod 容量兼容性均尚待实机确认。
6. 分别选择含船坞、兽坞、防御容量设施的样本：默认应跳过，开启强拆后可进入确认并显示风险提示；关闭开关应重新保护。检查更换基地和重新进入时恢复关闭。强拆开启时再加入唯一建筑、未知设施或模块／建筑施工，应仍无法执行。
